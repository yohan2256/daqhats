# PiSLM 프로토콜 개정안 — `pislm/3` → `pislm/4`

**대상:** `pislm.py` (Raspberry Pi 측) 구현자
**목적:** 바닥충격음 측정에서 시간축 신뢰성을 확보한다.
**상태:** 제안. 노트북 측 클라이언트와 시뮬레이터에는 이미 구현·검증되어 있으므로,
Pi 측이 `pislm/4` 를 내보내기 시작하면 그날로 붙는다.

개정은 네 가지다.

| # | 내용 | 와이어 변경 | 대역폭 비용 |
|:-:|---|---|---|
| 1 | 모든 스트림 프레임에 **시작 샘플 인덱스** | 있음 (페이로드 헤더 +8 B) | 프레임당 8 B (현장 실측 기준 약 0.01%) |
| 2 | `started` 이벤트에 **시각 원점(epoch)** | 없음 (JSON 필드 추가) | 0 |
| 3 | **과부하(클리핑) 이벤트** | 없음 (신규 이벤트) | ~0 |
| 4 | **백프레셔 정책 명확화** — 레벨 프레임은 드롭 금지 | 없음 (동작 변경) | 0 |

---

## 0. 왜 필요한가

현재 프로토콜에서 **프레임이 유실되면 클라이언트는 그 사실도, 유실량도 알 수 없다.**

§6은 느린 클라이언트에 대해 오래된 프레임을 버린다고 명시한다. 이때 클라이언트가 보는 것은
그냥 "다음 프레임"이다. 100 ms가 사라졌는지 3초가 사라졌는지 구분할 방법이 없고,
에러도 나지 않는다. 그 시점 이후의 모든 시간축이 조용히 밀린다.

이것이 바닥충격음 측정에서 문제가 되는 이유:

- **중량충격음(뱅머신·고무공)** 은 타격 1회마다 Lmax를 뽑아 평균한다. 타격 시점이 밀리면
  엉뚱한 구간에서 최대값을 집는다.
- **`get_raw` 로 받은 파형이 라이브 스트림의 어느 지점인지** 알 수 없다. 사후 재분석과
  실시간 관측을 대조할 수 없다.
- **성적서에 측정 시각을 기록할 수 없다.** 스캔 시작 이후 경과 시간조차 프레임 개수를
  세어 추정하는 수밖에 없는데, 그 추정이 바로 유실에 취약하다.

리샘플링(§4)은 이 문제를 풀지 **못한다.** 리샘플링이 제거하는 것은 두 ADC 클럭의 상대
드리프트다. 모든 디바이스를 48 kHz 공통 격자에 올려놓아도, 격자에 뚫린 구멍의 위치를
모르면 그 뒤가 통째로 밀리는 것은 똑같다. **드리프트와 유실은 별개의 문제이고, 각각
별개의 해법이 필요하다.**

## 1. 시작 샘플 인덱스 (필수)

### 1.1 와이어 레이아웃

기존 고정 헤더 필드 **뒤**, `float64` 페이로드 **앞**에 `uint64` 하나를 삽입한다.
5바이트 프레임 헤더(type + length)는 그대로다.

```
                        pislm/3                          pislm/4
DATA        0x01  [u32 device]                    [u32 device][u64 start_index]
LEVEL       0x04  [u32 channel]                   [u32 channel][u64 start_index]
BAND        0x03  [u32 band][u32 channel]         [u32 band][u32 channel][u64 start_index]
BAND_LEVEL  0x05  [u32 band][u32 channel]         [u32 band][u32 channel][u64 start_index]
RAW_DUMP    0x06  [u32 dump_id][u32 device]       [u32 dump_id][u32 device]
                  [u32 chunk][u32 is_last]         [u32 chunk][u32 is_last][u64 start_index]
MSG         0x02  (JSON, 변경 없음)                (JSON, 변경 없음)
```

바이트 순서는 기존과 같이 **리틀엔디언**. `u64` 를 쓰는 이유는 51.2 kHz에서
`u32` 가 약 23시간 만에 넘치기 때문이다 — 무인 장시간 측정에서 실제로 도달한다.
`u64` 는 같은 조건에서 1,100만 년이다.

샘플 개수 계산식도 그에 맞춰 8씩 늘어난다:

```
DATA        samples = (length - 12) / 8 / num_device_channels
LEVEL       samples = (length - 12) / 8
BAND        samples = (length - 16) / 8
BAND_LEVEL  samples = (length - 16) / 8
RAW_DUMP    samples = (length - 24) / 8
```

### 1.2 의미 — 어느 격자의 인덱스인가

`start_index` 는 **그 프레임 안 첫 샘플의 인덱스**이며, **각 스트림이 자기 자신의
레이트로 세는 값**이다. 하나의 전역 카운터가 아니다.

| 프레임 | 기준 레이트 | 인덱스 0의 의미 |
|---|---|---|
| `DATA` | 해당 디바이스의 유효 레이트 (리샘플 active면 `resample.output_rate`, 아니면 `actual_rate`) | 스캔 시작 후 그 디바이스의 첫 샘플 |
| `LEVEL` | `level.output_rate` | 스캔 시작 후 첫 레벨 출력 |
| `BAND` / `BAND_LEVEL` | `BAND` 는 그 밴드의 `decimated_rate`, `BAND_LEVEL` 은 `level.output_rate` | 각 격자의 첫 출력 |
| `RAW_DUMP` | 그 디바이스의 유효 레이트 — **`DATA` 와 같은 격자** | 〃 |

`RAW_DUMP` 가 `DATA` 와 같은 격자를 쓰는 것이 핵심이다. 이래야 사후에 받은 원파형을
라이브로 보던 레벨 스트림 위에 정확히 겹칠 수 있다.

`RAW_DUMP` 의 `start_index` 는 **각 청크의** 첫 샘플 인덱스다(덤프 전체의 시작이 아니다).
청크 경계가 프레임 경계와 정렬되지 않는다는 §2.5의 성질은 그대로 유지된다.

### 1.3 카운터 수명

- 인덱스는 **`start` 마다 0으로 리셋**된다. 스캔 하나가 하나의 시간축이다.
- 스캔이 도는 동안에는 **단조 증가하며 건너뛰지 않는다.** 서버가 프레임을 버려도
  카운터는 계속 간다 — 그래야 클라이언트가 구멍을 발견한다.
- 리샘플이 켜져 있으면 리샘플러 **출력** 기준으로 센다. 입력 샘플 수가 아니다.
- 클라이언트가 중간에 접속하면 그 시점의 인덱스부터 받는다. 0부터 다시 주지 않는다.

### 1.4 클라이언트가 이것으로 하는 일

```
expected = last_start_index + last_sample_count
if frame.start_index > expected:
    gap = frame.start_index - expected      # 사라진 샘플 수, 정확히
if frame.start_index < expected:
    # 중복/재정렬 — 프로토콜 위반이므로 로그를 남기고 버린다
```

노트북 측에는 `pislm.gaps.GapDetector` 로 이미 구현되어 있다.

### 1.5 검증 방법

시뮬레이터에 유실 주입 기능이 있다:

```bash
python pislm_sim.py --protocol 4 --drop 0.02   # 프레임의 2%를 의도적으로 버림
python -m pytest tests -q -k gap
```

검출된 갭의 총합이 주입된 유실량과 정확히 일치하는지 확인한다.

## 2. 시각 원점 (필수)

`started` 이벤트와 핸드셰이크에 `epoch` 블록을 추가한다. 샘플 인덱스 0이 **언제**였는지를
알려준다.

```json
"epoch": {
  "index": 0,
  "unix": 1785634779.123456,
  "utc": "2026-08-02T10:19:39.123456Z",
  "monotonic": 48213.559,
  "source": "system_clock",
  "note": "NTP 동기 여부는 보장하지 않음"
}
```

- `unix` / `utc` — 벽시계. 성적서의 측정 시각이 여기서 나온다.
- `monotonic` — Pi의 단조 시계. 벽시계가 NTP로 점프해도 경과 시간 계산은 이쪽이 안전하다.
- `source` — `"system_clock"` / `"ntp"` / `"gps"` 등. 클라이언트가 신뢰도를 판단한다.

변환은 자명하다:

```
wall_clock_time = epoch.unix + start_index / rate_of_that_grid
```

`start_index` 없이는 이 필드가 무의미하므로, 개정 1과 함께 들어가야 한다.

## 3. 과부하(클리핑) 이벤트 (권장)

현재 채널별 신호 포화를 알 방법이 전혀 없다. `overrun` 이벤트는 **데이터 유실**용이지
**신호 포화**용이 아니다.

뱅머신·고무공은 피크 레벨이 높아 ADC 포화가 실제로 발생한다. 포화된 구간이 섞인
측정값은 규격상 무효인데, 지금은 그 사실을 아무도 모르는 채 성적서까지 간다.

### 3.1 이벤트

```json
{"type": "event", "event": "overload",
 "device": 1, "channel": 4,
 "start_index": 2457600, "samples": 137,
 "peak": 5.02, "units": "V",
 "full_scale": 5.0}
```

- 채널당 최대 **레벨 출력 주기마다 한 번**으로 묶어 보낸다(초당 수천 개가 되면 안 된다).
- `start_index` 는 `DATA` 와 같은 격자 → 클라이언트가 포화 구간을 정확히 표시하고,
  그 구간이 포함된 측정을 자동으로 무효 처리할 수 있다.
- 판정 기준: ADC 풀스케일의 99% 이상인 샘플. 감도 보정 **이전**의 원시 전압 기준으로
  판정해야 한다(교정된 Pa 값으로 판정하면 감도에 따라 기준이 흔들린다).

### 3.2 누적 카운터

`get_config` / 핸드셰이크에 채널별 누적치를 함께 싣는다. 이벤트를 놓친 클라이언트도
"이번 측정 중 포화가 있었는가"를 사후 확인할 수 있어야 한다.

```json
"overload": {"0": 0, "1": 0, "2": 0, "3": 0, "4": 137, "5": 0}
```

`start` 마다 0으로 리셋한다.

## 4. 백프레셔 정책 명확화 (필수)

### 4.1 문서 모호성

§6은 "oldest live stream frames (**DATA and BAND**) are dropped" 라고 쓴다.
`LEVEL` 과 `BAND_LEVEL` 이 이 목록에 없는데, 이것이 **의도적 제외**인지 **표기 누락**인지
문서만으로는 알 수 없다. 측정 데이터의 신뢰성이 걸린 부분이므로 확정이 필요하다.

### 4.2 제안: 레벨 프레임은 드롭 대상에서 제외

§8의 자체 수치를 그대로 인용한다.

| 스트림 | 대역폭 |
|---|---|
| 레벨 전용 (`stream_raw=false`, 밴드 off) | **약 1 KB/s** |
| 원파형 6ch @ 51.2 kHz | 약 2,400 KB/s |

레벨 프레임을 버려서 절약되는 대역폭은 전체의 **0.04%** 다. 반면 그것을 버리면
사운드레벨미터로서의 주 출력이 손상된다. **비용과 손실이 완전히 비대칭**이므로,
레벨 프레임은 큐가 찼을 때 드롭이 아니라 블로킹으로 처리하는 것이 타당하다
(§2.5의 `RAW_DUMP` 와 같은 취급).

즉 드롭 정책을 다음과 같이 확정한다:

| 프레임 | 정책 |
|---|---|
| `DATA`, `BAND` | 드롭 가능 (best-effort) — 대역폭을 지배하므로 |
| `LEVEL`, `BAND_LEVEL` | **드롭 금지** — 크기가 무시 가능하고 측정의 본체이므로 |
| `MSG` | **드롭 금지** — 이벤트 유실은 상태 불일치를 낳으므로 |
| `RAW_DUMP` | 드롭 금지 (현행 유지) |

### 4.3 드롭 카운터 분리

지금은 `network.stream_frames_dropped` 하나에 합산된다. 무엇이 버려졌는지 알 수 있어야
클라이언트가 대응을 정한다(원파형만 잃었다면 `get_raw` 로 복구 가능, 레벨을 잃었다면
측정 자체를 다시 해야 한다).

```json
"network": {
  "stream_clients": 1,
  "stream_frames_dropped": 42,
  "stream_frames_dropped_by_type": {"DATA": 40, "BAND": 2}
}
```

기존 합계 필드는 하위호환을 위해 남긴다.

## 5. 버전 협상

### 5.1 핸드셰이크

```json
{
  "type": "handshake",
  "protocol": "pislm/4",
  "frame_layout": 4,
  ...
}
```

- `protocol` 문자열을 `pislm/4` 로 올린다.
- `frame_layout` (정수) 을 새로 둔다. 클라이언트가 문자열 파싱 없이 레이아웃을 고를 수 있다.
  이후 개정에서 JSON만 바뀌고 와이어 레이아웃은 그대로인 경우, 이 값을 올리지 않으면 된다.

### 5.2 전환 기간 대응

Pi 측 `config.ini` 에 스위치를 둔다.

```ini
[network]
protocol_version = 4    ; 3 = 기존 레이아웃 (구 클라이언트 호환), 4 = 인덱스 포함
```

기본값은 `4` 로 하되 `3` 을 남겨두면, 기존 `pislm_test.py` 나 다른 클라이언트를
한꺼번에 고치지 않아도 된다. 노트북 측 라이브러리는 **두 레이아웃을 모두 읽으며**,
핸드셰이크의 `frame_layout` 을 보고 자동으로 판별한다. 따라서 Pi 쪽만 바꾸면 된다.

### 5.3 클라이언트 측 판별 (구현 완료)

```python
version = handshake.get("frame_layout")
if version is None:
    version = 4 if handshake.get("protocol") == "pislm/4" else 3
```

스트림 포트도 접속 즉시 자체 핸드셰이크를 받으므로(§3), 첫 데이터 프레임이 오기 전에
레이아웃이 확정된다. 경합은 발생하지 않는다.

## 6. 구현 체크리스트 (Pi 측)

- [ ] 디바이스별 출력 샘플 카운터. **리샘플러 출력** 기준으로 셀 것 (§1.3)
- [ ] 레벨 출력 카운터 (`level.output_rate` 격자)
- [ ] 밴드별 데시메이션 출력 카운터 (`BAND` 는 밴드마다 격자가 다르다)
- [ ] 프레임 조립부 5곳에 `u64` 삽입
- [ ] `start` 시 모든 카운터와 과부하 카운터 리셋
- [ ] **프레임을 드롭해도 카운터는 계속 증가** ← 가장 틀리기 쉬운 부분
- [ ] `get_raw` 가 링버퍼에서 잘라낸 구간의 시작 인덱스를 계산해 청크마다 실을 것
- [ ] `started` / 핸드셰이크에 `epoch` 추가
- [ ] 감도 보정 **이전** 원시 전압에서 포화 판정 (§3.1)
- [ ] 백프레셔에서 `LEVEL` / `BAND_LEVEL` / `MSG` 제외 (§4.2)
- [ ] 드롭 카운터를 타입별로 분리 (§4.3)
- [ ] 핸드셰이크에 `frame_layout: 4`, `config.ini` 에 `protocol_version`

### 회귀 확인

노트북 측 시뮬레이터가 이 명세대로 동작하므로, Pi 구현 후 같은 테스트를 실장비에
겨눠 돌리면 된다.

```bash
python pislm_monitor.py <Pi주소> --seconds 60 --check-gaps
```

60초 동안 갭 0, `overload` 이벤트 0이면 정상이다.

## 7. 개정하지 않는 것 (검토했으나 제외)

- **디바이스 간 하드웨어 클럭 동기** — GPIO 트리거 + 리샘플링으로 충분하다.
  §4의 실측(300초에 0.15 ppm)이면 바닥충격음 용도에는 여유가 크다.
- **`float32` 스트리밍 옵션** — 대역폭이 절반이 되지만, 현장 실측에서 유선·무선 모두
  여유가 확인되었으므로(19.68 Mbps, 드롭 0) 정밀도를 깎을 이유가 없다.
- **Pi 측 파일 저장** — 링버퍼 + `get_raw` 로 충분하고, SD카드 수명과 용량 관리라는
  새 문제를 들여올 이유가 없다. 연속 기록은 노트북이 맡는다.
- **잔향시간(T20) 측정** — 계측기가 아니라 측정 절차의 영역이다. `get_raw` 원파형에서
  노트북이 슈뢰더 적분으로 계산한다.
